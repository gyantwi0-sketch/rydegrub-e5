# Relational domain persistence foundation (#1)

This PR introduces a **server-only, versioned SQLite domain schema** at `lib/server/domain-store.mjs` and integration tests. Native accounts now connect through the identity bridge and authenticated cart/draft APIs (see `commerce-api.md`). The browser demo cart is not yet connected and no payments are collected. Issue #1 stays open until those UI/API integrations are implemented. Authenticated endpoints expose only owner-scoped carts, quotes and unpaid drafts.

## Scope and entities

`DomainStore(DATA_DIR)` creates `domain.sqlite` with WAL, SQLite foreign keys and transactional migrations. The versioned schema includes `accounts`, `stations`, `vendors`, `catalog`, `journeys`, `carts`, `cart_lines`, `orders`, `order_lines`, `payment_attempts`, `fulfilment_events`, state transition history and idempotent order creation records. Future migrations must be added sequentially to the migration array with user_version incremented in the same transaction. Unknown/newer schema versions cause a startup failure, never a silent reset.

All amounts are **integer paise**, currency `INR`, and catalog prices are always read from the server database. Owner IDs are fixed-length opaque, 64-character keys generated by a trusted issuer identity mapping. The journey table accepts only a server-produced, keyed 64-character hex PNR fingerprint, **not raw PNRs**. Secrets used for that fingerprint must be managed outside the repo; the current repository has no PNR provider adapter. Passenger names, telephone numbers, emails, coach and seat data are deliberately omitted from journeys/order events at this stage. User email/password fields are reserved for later credential registration; native registration uses the separate AccountStore; the commerce identity bridge does not copy credentials.

## Internal methods and security guarantees

- `createAccount(owner, subject)` — trusted identity adapter only; `ensureAccount` binds verified native sessions in the commerce API.
- `addStation`, `addVendor`, `putProduct` — trusted catalog/operations adapter only; do **not** expose these as unauthenticated APIs.
- `addJourney(owner, snapshot)` — requires preverified station/train metadata and **keyed** PNR digest. Do not send browser PNR input directly to this method.
- `readCart(owner)`, `replaceCart(owner, expectedVersion, items)` — owner-scoped, strict allowed fields, max 30 distinct SKU lines, quantities 1–99, per-item availability checks, <=₹20,000 maximum and optimistic cart version. Both cart update and validation run atomically.
- `createDraftOrder(owner, journeyId, expectedCartVersion, idempotencyKey)` — owner/journey/cart checks and server-side current prices in a single transaction; freezes a snapshot of item name and price. Drafts are not paid/confirmed orders, stock reservations or fulfilment requests.
- `readDraft(owner, id)` — strict owner-scoped projection; never returns all database fields.

The commerce HTTP layer derives identity from a verified native session; it never accepts client-selected owners. Cart replacement and draft creation are the only exposed domain writes. Server-only state transition methods now exist (see `docs/state-machines.md`), but no verified payment adapter or live fulfilment route invokes them. Draft creation requires a durable idempotency key (see `docs/order-idempotency.md`). Real checkout/payment integration must still validate inventory/capacity, verify payment webhooks and use provider state evidence. Do not treat an accepted `draft` as a payable order.

## Operational configuration

For persistent single-host Node 24 deployments, set a **new private absolute data directory** for `DomainStore` outside `public/`, `.next/` and other web-served paths. Create it with restrictive permissions (0700; files private). SQLite WAL on an ephemeral/serverless runtime or independent multi-host filesystems is **not** a distributed database; deploy only on a persistent local volume and back up/restore all SQLite files consistently. Encrypt storage and backups at rest, restrict database access, define retention/deletion plans for account and order records and monitor capacity without logging request bodies, phone numbers, raw PNRs or payment payloads.

No real account database migration from production was attempted: native account linking is now implemented, but deployment acceptance and legacy identity reconciliation remain required. Existing MEDIA, TRACKING and PROFILE databases are separate and remain unchanged. Data migration/identity reconciliation is required before combining them; never infer owner identity from user-submitted email, PNR, URL or headers.

Run `pnpm test`, `pnpm lint`, `pnpm typecheck`, `pnpm build`. Tests cover migrations/restarts, foreign keys, cross-account isolation, stale cart versions, catalog repricing, inactive SKUs, unexpected fields and raw PNR exclusion. Operator smoke-testing and the separate API/identity/checkout work remain required before closing issue #1.
