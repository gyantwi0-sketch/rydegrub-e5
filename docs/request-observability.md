# Safe request correlation and error reporting (#25)

Media, order-tracking and profile API handlers now generate a new random UUID v4 server-side **for each request**, including authenticated reads, mutations and failures. Each response includes `X-Request-ID`, `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer` and `X-Content-Type-Options: nosniff`. Caller-supplied `X-Request-ID` and other forwarded headers are **never trusted**. Any existing private `Vary`, rate-limit Retry-After or endpoint-specific resource headers are preserved.

Each handler emits **one** JSON-line structured record to the standard server logger with only allowlisted, non-personal keys: `event: "http_request"`, server-generated `requestId`, fixed service name (`media`, `tracking`, `profile`), fixed action name (e.g. `read`, `upload`), status code and bounded duration in milliseconds. Do not add URL paths, query strings, source IP, account identifiers, owner hashes, emails, names, OTP codes, passwords, PNRs, JWTs, bodies, headers, payment details or exception stacks to this record. Ingress, hosting/CDN, APM and provider SDKs must **separately disable** capture of sensitive HTTP content; this helper cannot erase logs recorded upstream.

Errors continue using the established minimal `{ "error": "safe message" }` JSON envelope for backwards compatibility. Only explicit, server-defined HTTP errors are returned with their known 4xx/503 status and controlled message. Unknown exceptions are consistently converted into a 503 with a generic service-unavailable error. Neither exception details nor stack traces are reflected to clients or logged. 404 privacy semantics on tracking (unrecognized/unauthorized IDs) are preserved; the new request ID cannot be used to enumerate orders.

## Integration and verification
Run `pnpm test`, `pnpm lint`, `pnpm typecheck` and `pnpm build`. Tests verify UUID uniqueness, known-vs-unknown error handling, per-request correlation headers, consistent private response controls and logging that never includes malicious client input. Requests with missing production configuration fail safely. A broken logger cannot break an API response.

Production monitoring should aggregate status buckets, duration and total attempts without user-level dimensions. Administrators can use the response request ID to locate the corresponding safe server record when diagnosing 503s. Log retention and access control remain a deployment responsibility. It is **not** a tracing system with multi-service spans: upstream proxies and the SMS provider require separate integration to propagate request IDs, without exposing passenger data. The demo checkout, user account login, PNR provider and catalog PR #67 must be integrated independently and must adopt this handler policy when new routes go live.
