# Transactional security audit (#15)

The account, profile, media, tracking and domain SQLite stores install versioned `security_audit` tables and fixed database triggers. Every relevant committed mutation inserts an event in the same transaction: if insertion fails, the business mutation rolls back too. Failed domain transitions create no misleading successful event. Failed credential verification appends a generic failed-sign-in event without retaining the attempted email.

Coverage includes account registration, verification, password changes, session creation/removal, verification/reset challenge lifecycle, profile and consent changes, phone challenges, upload lifecycle, tracking creation/updates/revocation, cart writes, order/checkout transitions, payment state transitions, vendor/catalog/station administration and fulfilment events. Only existing trusted server mutation paths are covered; future vendor dashboards and provider webhooks must use audited stores and add tests when introduced. The separate catalog branch must install the same audit mechanism before it is merged.

Events store a generated sequence, fixed event name, timestamp, optional opaque affected-owner key, safe entity ID, and allowlisted state transition. They never store passwords or password hashes, raw session/verification/tracking tokens or their digests, emails, names, phones, OTPs, payment provider references, prices, raw PNRs or PNR fingerprints. Events identify the service boundary (`actor_class=service`), not an invented human operator. The affected-owner key is correlation context, not proof of a staff identity. A future staff/admin identity layer must supply its separately verified actor context.

Application SQL cannot UPDATE, DELETE or INSERT OR REPLACE an existing audit event. This is append-only enforcement within the application database, not a claim that a host/database administrator cannot tamper with files or schema. Use restrictive private-volume permissions, encryption at rest, consistent backups and independent restricted/WORM log archival for protection against privileged tampering. No external archive was provisioned here.

Audit schema versioning is independent of each business schema's user_version. Unknown audit schema versions fail startup. Existing historical business data is not backfilled with fabricated events; recording begins after the store opens with this release. Application rollback must preserve the installed audit triggers and tables.

No user-facing audit dump endpoint is exposed. Authorized operators can inspect counts and event sequences using read-only database access. Treat opaque owner/entity keys as sensitive pseudonymous data. Establish an approved retention/archive schedule and access policy before production; any retention deletion requires an explicit privileged maintenance procedure outside application endpoints, with its own recorded approval. Ordinary account deletion must not silently remove security records or bypass these triggers. This change does not claim to implement the separate data-export/deletion workflow (#11).

Tests exercise atomic rollback on audit failure, append-only guards including replacement, privacy exclusions, authentication, profile/media/tracking events, and successful versus rejected domain/payment transitions. A successful internal payment event still requires independently verified gateway evidence in the gateway adapter; the audit is not evidence that real funds moved.
